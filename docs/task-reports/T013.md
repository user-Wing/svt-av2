## 6. `frames` 语义修正（P1 验收项，本轮主要行为改动）

**修复前（缺陷）**：`--frames 2` 与多帧源默认值会**静默产出多个 21B still-picture 拼接**，
exit 0。实测 `p1_frames_2.av2` 42B = 两个**完全相同**的 21B 单帧流，第二帧并非
不同图案 → 正是契约 §7/§8 与任务书禁止的
"默认拼接多个 21B still-picture 流就满足视频序列"。

**修复后**：多帧请求**明确拒绝**，不静默丢帧，且不留误导性输出文件。

| 请求 | 3 帧源 | 1 帧源 |
|---|---|---|
| 默认（全部） | **拒绝** exit 15，无文件 | 1 帧 exit 0，21B |
| `--frames 0` | exit 0，0 帧（0 字节文件） | — |
| `--frames 1` | exit 0，1 帧 21B | — |
| `--frames 2` | **拒绝** exit 15，无文件 | — |
| `--frames 17` | **拒绝** exit 15，无文件 | — |

设计说明（AGENTS §1，明确假设与取舍）：
- 单帧能力上限的唯一记录点是 `codec.h` 的 `SVT_AV2_MAX_ENCODABLE_FRAMES`；
  T015 交付多帧合法方案后由 T013 放开此值并实现 PTS/EOS 生命周期（P4）。
- **默认（`-1`=全部）也要拒绝**：先 `app_count_available_frames()` 数帧，
  在**写任何字节前**判定。若只编码第一帧就返回成功，等于静默丢帧。
- **`--frames 0/1` 在 3 帧源上仍允许**：请求被显式限定在能力内，不属于"要求多帧"。
  `--frames 0` 产生 0 字节文件是真实的"编码 0 帧"结果，非误导产物。
- 拒绝发生在 `fopen(output)` **之前**，故不会留下 0 字节"看似合法"的文件。
- 新增退出码 `SVT_AV2_APP_EXIT_UNSUPPORTED_FRAMES = 15`（与 14=不支持输入区分）。
