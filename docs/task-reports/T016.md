## 5. S4 — 连续 1000 帧（驱动就绪；长跑 BLOCKED，且依赖箭头已澄清）

### 5.1 驱动设计要点（`tools\run_stability.py`）

- **单进程单次调用**：帧数由一次 `--frames N` 请求，绝不靠重启进程 N 次凑数。
- **逐帧指纹**：输入第 k 帧行 0 前 4 字节写入 k 的大端指纹；从 decoder 输出反推，重复首帧/丢帧会硬 FAIL。
- **帧数取自 decoder**，不靠文件长度。
- **泄漏结论来自检测器**（ASan/LSan/valgrind），RSS 仅趋势。
- **峰值内存**：编码期间采样工作集（Windows `GetProcessMemoryInfo` / Linux `/proc/<pid>/status` VmRSS），记入 `peak_rss`。
- **`--frames ≥ 2` 的拒绝按 T013 要求作"断言"**：以 **app 退出码 15（`SVT_AV2_APP_EXIT_UNSUPPORTED_FRAMES`）** 为判据（非消息文本），命中即 BLOCKED 并记依赖箭头；**其余非零退出码一律 FAIL**——防止未来某构建"返回 0 却只输出 1 帧"被静默放过（这正是防静默拼接的护栏）。本轮已按此改写驱动。

自测（`tools\test_check_platform.py`）已验证：能检出重复首帧、丢帧、错帧数；用法错误 exit 2。**SELF-TEST PASS**。

### 5.2 多帧是"冻结的显式拒绝"，不是"待接线"（T013 P1 澄清，T016 采信）

### 7.1 方法学记录：`ctest` 无 per-test 超时（00 最终裁定：不落 TIMEOUT）

本机 CTest 未设 `TIMEOUT` 属性，**真死循环会无声卡住整个平台矩阵**（T016 曾亲历 T009 并发编辑窗口导致的 Debug 死循环；00 亦撞到同一瞬时态）。T016 曾建议为各 `add_test` 设宽 `TIMEOUT`（120–300s）或对 `ctest` 加外部超时并记 FAIL 而非挂起。**00 最终裁定（2026-10-07）：不落公共 `TIMEOUT`** —— 理由：给所有测试设 TIMEOUT 会引入"慢机器误判 FAIL"的新风险，而当前真死循环只出现在**并发编辑窗口**（瞬时态）。**采纳替代方案**：**跑矩阵前先确认源稳定**（已写入根 `AGENTS.md` **§7.7 构建与产物纪律**第 5 条）。T016 同意该裁定；若将来出现**非并发场景**的死循环，再由 00 单独为 `runner_*` 设 TIMEOUT。

**注册数非常量（方法学，00 已采纳）**：CTest 注册数**随时间增长、无唯一值**，它等于"该 build 目录最后一次 configure 时的注册面"。T016 重跑矩阵时**重新 configure + 记 `generated_at` + 当刻实测注册数 + `source_hashes`**；不预告、不套用他人数字。建议**不再跨会话追发注册数**（每发即过时），一律以快照自证值为准。

> **T013 补充的实例（同一"时点差"）**：T016 早期记 Win `ctest 26/26`（A1 落盘时点）；T013 现测 **28** —— 增量 = `compare_recon_self_test` + `runner_oracle_smoke`（注册于 `tests\CMakeLists.txt:326/:332`，源自 T014 的 `compare_recon.py`）。**26 与 28 不矛盾，只是时点不同**。T016 实测 `ctest --test-dir build\T016\Win-Release -N` = **28**，与 T013 一致。=> 又一"注册数非常量"的活例。

> **00 定论（2026-10-07，T016 与 00 双向实测后采纳）**：① 注册数 = 该 build 目录**上一次 configure 时的树快照**，随树增长而变，**不是常量**；② 因此**不得作为验收判据**；③ 唯一正确做法 = "**跑矩阵前先 configure，再实读该目录 `ctest -N`**"；④ 权威值只对"当轮、该目录"有意义。**T016 双向实测佐证**：`00-wsl-gcc`=22、`00-wsl-gcc-t012`=24、`00-wsl-gcc-verify`=**27**（00 报 25 后又变）、`build\T016\Linux-GCC-Release`=**27**、`build\00`(Win)=**28**、`build\T016\Win-Release`=26；连 00 的本轮权威值也在分钟级内变动，**正实证了"非常量"**。T016 已把该定论**转告 T014**。

### 7.4 T016 自身**探针缺陷**更正（"memset 消警无效"是错的）

```
pre-fix 无 memset                    -> exit 1
pre-fix + memset(packed_dq,0,sizeof) -> exit 0   ← 消警
pre-fix + = {0}                      -> exit 0   ← 消警
```
**根因 = T016 探针 bug**：当时源码有**两处** `packed_dq[SVT_AV2_TX_MAX_PELS]` 声明，探针用"**首个匹配 `replace()`**"，改到了**错的那一处**；"实测"的实为**未改动源码**（**静默空替换**），产生假的"仍报"。=> **不是 GCC 行为差异，是取样错误**。已在 `t012_fix_insufficient_gcc_release.md` 加 CORRECTION，并留存修正脚本 `artifacts\T016\S1\_t016_settle_memset.sh`（`CC48FDC0..`）。
> **方法学教训（T016 自记）**：探针/替换脚本必须**断言替换命中**（锚点唯一或计数校验），否则会静默测到未改动的源——与"hash 只信实测"同类：**不信脚本以为做了什么，要看它实际做了什么**。
