# T009 尺度表（冻结，供 T010/T011/T012 与 00 引用）

来源：`avm/av2/common/idct.c`、`avm/av2/common/common_data.h`、`avm/av2/encoder/encodemb.c`。
本表与 `Source/Lib/Transform/transform.c` 的实现逐字对应；任何改动都必须同步本表并通知 00。

## 1. 变换类型与尺寸

- 类型：**DCT_DCT only**（二维可分离 DCT-II）。不含 ADST / IDTX / DDTX / FDDT / 二次变换 / 跨色度变换。
- **M2 首版真实尺寸（00 裁决 (A)，冻结）**：**luma TX_64X64（`tx_scale = 2`）+ chroma TX_32X32（`tx_scale = 1`）**。
  这不是可选扩展，是 M2 首版路径本身（`tx_mode_select = 0` -> `TX_MODE_LARGEST` -> 顶层 64x64 `PARTITION_NONE`）。
  （此前"建议首版 8x8"的表述已由 00 裁决取代，作废。）
- 已实现（`pels <= 256`，`tx_scale = 0`，仍是有效几何）：`4x4, 8x8, 16x16, 4x8, 8x4, 4x16, 16x4, 8x16, 16x8`。
- **不实现**：`TX_16X32/32X16/16X64/64X16/8X64/... `等 32/64 矩形家族尺寸（本轮帧头 `TX_MODE_LARGEST` + 64x64 `PARTITION_NONE` 不会产生它们）。
- 32/64 的实现要点：
  - **逆**（`idct.c:648-751`）：工作核钳到 32x32，`skipWidth = skipHeight = 0`，**32 点核两遍 + 2×2 复制上采样**。
  - **正**（`hybrid_fwd_txfm.c:952-1008`）：TX_32X32 走 32 点核两遍；TX_64X64 走 **64 点核两遍**，高半部置零后 repack 到前 32x32。正逆**不同构**。

## 2. tx_scale / log_scale

```
tx_scale(w,h) = (w*h > 256) + (w*h > 1024)        // idct.c:761-765
log_scale     = tx_scale                          // encodemb.c:819
```

| 尺寸 | pels | tx_scale = log_scale |
|---|---|---|
| 4x4, 4x8, 8x4, 8x8, 4x16, 16x4, 8x16, 16x8, 16x16 | <=256 | **0** |
| 16x32, 32x16, 32x32 | 512 / 1024 | 1 |
| 32x64, 64x32, 64x64 | 2048 / 4096 | 2 |

关键边界：**16x16 = 256 pels 不 > 256，故 tx_scale = 0**（不是注释里说的 Q2）。

(A) 裁决相关（**已实现并冻结**）：**chroma TX_32X32 -> tx_scale = 1**（1024>256 真、1024>1024 假），
**luma TX_64X64 -> tx_scale = 2**。两者都不再是 0，T010 量化器须支持 `log_scale = 1/2`。

### 2a. 调用约定（T010 发现，T009 复核属实，**必须遵守**）

`tx_scale(w,h)` 的 `w,h` 是**原始变换几何**，**不是**系数承载网格。
依据：`idct.c:761-765` 的 `av2_get_tx_scale()` 用 `tx_size_2d[tx_size]`，而 `tx_size_2d[TX_64X64] = 4096`
（原始几何），与该尺寸实际只承载 1024 个系数是**两个无关问题**。

```
svt_av2_tx_scale(64, 64) = 2   <-- 正确：原始 tx_size
svt_av2_tx_scale(32, 32) = 1   <-- 错误：这是 TX_64X64 的承载网格，别照它传
```

**后果**：若因 TX_64X64 被 repack 成 32x32 就把 tx size 传成 `(32,32)`，`tx_scale` 掉到 1，
反量化少移一档 → **所有 `dqcoeff` 系统性偏大 2x，且不报任何错**。

**为什么容易踩**（T009 补充的可观测性判据）：

```
svt_av2_tx_coeff_count(64, 64) == svt_av2_tx_coeff_count(32, 32) == 1024
```

即 **count 无法区分 64x64 与其承载网格 32x32，只有几何能区分**。这正是 (甲) 裁决（出口 1024）之后
风险升高的原因。已冻结进 `transform.h` 的注释，并在 `test_transform.c` 加 2 条锚定断言。
`tx_scale` 本身**不需要**改规则，只需调用方传对几何。

## 2b. TX_64X64 / TX_32X32 的系数个数（纠正 00 早期给 T011 的 4096）

`av2_get_max_eob`（`avm/av2/common/blockd.h:3477-3490`）：

```
TX_64X64 -> 1024        （特判，不是 4096 = tx_size_2d）
TX_32X32 -> 1024        （走默认 = tx_size_2d）
```

即**码流侧 TX_64X64 与 TX_32X32 都只承载 1024 个系数**（32x32 网格）。佐证：
- 编码：`hybrid_fwd_txfm.c:1003-1008` 64 点算完后 repack 到前 32x32（`skipWidth = 64-32 = 32 ≠ 0`）。
- 解码：`idct.c:705,708` 逆变换 `memcpy(tmp, input, min(1024, w*h))` 只读 1024。

**T009 出口契约（冻结，= 00 裁决 (甲)）**：
```c
svt_av2_tx_coeff_count(w,h) == min(w,32) * min(h,32) == av2_get_max_eob(tx_size)
```
- TX_64X64 → **1024**（32x32 网格，**不是 4096**）；TX_32X32 → 1024。
- `w,h <= 32` 时即 `w*h`，不破坏 ≤16x16 家族。
- 布局：raster 行主、DC@0；64x64 即 32x32 网格的行主。
- (甲) 唯一自洽的理由：正变换 repack（`hybrid_fwd_txfm.c:1003-1008`，`memcpy(coeff+row*32, coeff+row*64, 32)`）与逆变换**入口打包**
  （`idct.c:712-716`，`if (skipWidth) for(y) memcpy(block+y*width, tmp+y*32, 32)`）**互为镜像**，且与 `max_eob`、scan 表三方一致。

**闭式是精确的（不是"仅 64x64 特例"）——T009 独立穷举复核 25/25**：

`min(w,32)*min(h,32)` 对**全部 25 个 `TX_SIZES_ALL`** 与真实 `av2_get_max_eob` 逐项相等。
证据：`artifacts/T009/verify_max_eob_closedform.c`（**自包含**：逐字转写 `common_data.h:578-581/586-589/613-616`
的 `tx_size_wide/high/2d` 与 `blockd.h:3477-3490` 的 `av2_get_max_eob`，不 include AVM 头、不依赖 T010 的表；
自带"转写表自检"以防双侧同错）。Release + Debug：**checks 25 / failures 0；表自检 0 失败**。

**9 个几何会让"朴素 `w*h`"出错**（不只是 64x64），这正是不能硬编码的原因：

| 几何 | `w*h`（朴素，错） | `max_eob` = 闭式（对） |
|---|---|---|
| 64x64 | 4096 | **1024** |
| 32x64, 64x32 | 2048 | **1024** |
| 16x64, 64x16 | 1024 | **512** |
| 8x64, 64x8 | 512 | **256** |
| 4x64, 64x4 | 256 | **128** |

=> 契约应写**闭式**，不要硬编码（否则 16x64=512、8x64=256、4x64=128 这些会被漏掉）。
**注**：这 9 个中除 64x64/32x32 外，其余 7 个属 §3.2"本轮未实现"的矩形家族，本轮不产生；
登记闭式是为了将来纳矩形时不必重推。

## 2d. 正变换方案选择（00 §三 给了自由度，T009 选 (a)）

00 裁定：M2 的 DoD 是"internal recon == AVM decoder 输出"，两者共用同一逆变换，故**正变换是编码器侧自由度，不要求与 AVM 逐位相同**；
但**逆变换必须与 AVM 逐位一致**。T009 选择：

- **(a) 照 AVM 做（已实现）**：TX_32X32 走 32 点核两遍；TX_64X64 走 **64 点核两遍** + 高半部置零 + repack 到前 32x32。
- **理由**：
  1. 硬性要求（逆变换逐位一致）与正变换方案无关，已由 `verify_32_64.c` 独立证明；
  2. 选 (a) 使本模块**同时**满足"码流合法"与"与参考编码器逐位可比"，为将来帧级码流对齐（T013/T014）
     少一个变量（若用 (b) 的 32 核 + 下采样，参考解码器仍能解，但我的码流与 AVM 编码器不再逐位可比）；
  3. (a) 的正变换实现量已支付（64 点核已落盘并 bit-exact 验证），无额外成本；
  4. 未来若需插入 `tx_type!=DCT_DCT` 或二次变换，AVM 的 `fwd_transform_1d` 调度结构可直接扩展。
- 附：即使选 (b)，`svt_av2_tx_coeff_count` 仍是 1024，逆变换仍逐位一致；本表的 shift/scale 与选择无关。

## 2c. 32/64 上正逆不同构（影响 coeff 长度契约）

- 逆（`idct.c:648-751`）：`width = height = min(32, tx_wide) = 32`；`skipWidth = skipHeight = 0`；
  **32 点核 + 2×2 复制**；`sqrt2` 用真实 `log2`（64x64: 6+6 偶）-> **不触发**；入口只读 **1024**。
- 正（`hybrid_fwd_txfm.c:952-1008`）：`width = height = 64`（**无 min(…,32)**）；
  `skipWidth = 32 ≠ 0`；**64 点核**（`fwd_txfm_dct2_size64_c`），高半部按 `zero_line` 置零，再 repack。
- 因此"64x64 只是 32 核 + 复制"**仅对逆成立**，正变换需要 64 点核。

## 4. 与 T010 量化的对账

- 正变换出口 = 该几何的方块变换系数（raster），**T009 不在出口做任何 `>> tx_scale` 降尺度**。
  `quant_common.c:44-55` 的 “transform returns Q2/Q1” 是描述性说法，真正落实降尺度的位置是**量化器**：
  `encodemb.c:376`（正量化步长按 log_scale）、`decodetxb.c:526/673`（反量化 `dq >> tx_scale`）。
  因此降尺度的唯一责任方 = 量化器。对 `tx_scale == 0` 的 ≤16x16 几何，出口系数等价于 Q3，与 T010 精确自洽；
   对 TX_32X32（1）与 TX_64X64（2），出口系数分别是 Q2 / Q1，**仍由 T010 在量化/反量化侧落实降尺度**。
   （扩尺寸时若把降尺度算到 transform 出口会造成双重/漏降尺度，见 T009 发给 T010 的契约澄清。）
- 反量化：`dq = ROUND_POWER_OF_TWO(level * dequant, 3) >> tx_scale`，clamp `[-32768, 32767]`。
  ≤16x16 时 `tx_scale == 0`，故 `dq = ROUND_POWER_OF_TWO(level * 704, 3)`（base_q_idx=100，`qlookup(100)=704`）。
- 正量化（T010 侧）：`deadzone = ceil(dequant / 2^(1 + log_scale + 3))`，
  `level = ((abs_coeff + ROUND_POWER_OF_TWO(33, log_scale)) * 11915) >> (16 - log_scale + 4)`。
  `log_scale = 0/1/2` 分别对应 ≤16x16 / TX_32X32 / TX_64X64（T010 已实现并锚定）。
  **注意 AVM 的正量化在舍入之后还有一步 `>> log_scale`**（`avm/av2/encoder/av2_quantize.c:118-121`，
  `ROUND_POWER_OF_TWO_64(abs*dequant, QUANT_TABLE_BITS) >> log_scale`），`log_scale == 0` 时是恒等，
  故 ≤16x16 时被掩盖；T010 已据此修好漏移位。反量化侧同理是 `>> tx_scale`（`decodetxb.c:526/673`）。
- 舍入：T009 的 `svt_av2_tx_round_shift(v,b) = (v + (1<<(b-1))) >> b`，算术右移（floor）。形式与 T010 的 `ROUND_POWER_OF_TWO` 相同；负数极端边界需两侧一致。
  **顺序纪律**：本模块所有"先舍入后移位"的位置（`svt_av2_tx_round_shift` 内部即 `(v + half) >> b`）
  都是 round-then-shift，且 32/64 新路径（`NewSqrt2`/`NewInvSqrt2` 归一化）沿用同一函数，顺序不可交换这一点已由
  AVM bit-exact 比对覆盖。T010 §2 的漏移位正是这类顺序问题的反面案例，已交叉确认本模块无同类问题。
- **正变换无内部饱和**：`svt_av2_fwd_transform()` 对 `coeff` 不做任何 clamp/saturate（累加为 `int64_t`），与 AVM `fwd_txfm()` 一致。唯一拒绝路径是输入 residual 出 `[-255,255]` 时返回 `SVT_AV2_TX_ERR_RANGE`（不静默钳位）。因此 coeff 幅度由输入 residual 与该几何的 `fwd_tx_shift` 决定，不由本模块钳位；T010 的 `LEVEL_OVERFLOW` 分支在当前冻结输入下不可达但依然可达（上游喂超范围 residual 会先被 T009 拒绝）。
- 数据流方向（冻结）：T009 生产 `coeff`、消费 `dqcoeff`；T010 从 `coeff` 生产 `qcoeff`+`dqcoeff`；T009 逆变换消费 `dqcoeff`；T012 消费逆变换的 residual。

## 4b. "正变换出口无 tx_scale" 的独立复核（T009 逐行核实，2026-10-07）

对 `hybrid_fwd_txfm.c` 全文检索 `tx_scale` / `get_tx_scale`，**恰好 2 处**，均不在 lossy DCT 路径：

| 位置 | 上下文 | 是否影响本配置出口 |
|---|---|---|
| `:27` | `av2_lossless_fwd_idtx_c`：`scale_bits = 3 - av2_get_tx_scale(...)`，用于 `coeff = src_diff * (1 << scale_bits)` | **否**。lossless 专用，且是**升**尺度 `2^(3-tx_scale)`，方向与降尺度相反 |
| `:1140` | 二次变换 IST 的 `sec_tx_coeff_energy`（`av2_sum_squares_i32`）——能量估计**指标**，非系数输出 | **否**。IST 不在本轮范围 |

- **lossy DCT 主路径 `fwd_txfm_c(:948-1018)` 零 `tx_scale` 引用**：出口只做 `fwd_tx_shift[]`（`:995-1001`）+ sqrt2 归一（`:1013-1017`）。
- 路径选择：`av2_fwd_txfm(:1020-1029)` 仅当 `lossless && tx_type==IDTX` 才走 `av2_lossless_fwd_idtx`，否则走 `fwd_txfm()`；我们配置恒走后者。
- 因此本模块"出口不降尺度、降尺度唯一责任方 = 量化器"的结论，在 **lossless 与 IST 之外**是干净的。
  **警示**：若将来开 lossless 或 IST，`:27` / `:1140` 是**另一套**尺度语义（且方向相反），不得与本表的 `tx_scale` 混用。

## 5. 逆变换输出范围

- 输出为 **residual**（`int16_t`），clamp 到 `[-256, 255]`（`col_rng`，`1<<8`），**不是** `[0,255]`。
- 加预测与像素级 clip 归 T012。

## 5b. coeff 幅度（T010 实测 + T009 独立复算，全 11 几何）

T010 用真实 `svt_av2_fwd_transform` 输出驱动做最坏合法输入扫描（`artifacts/T010/probe_coeff_range.c`
-> `coeff-range-32-64-probe.log`）；T009 又用自己的搜索独立复算了一遍
（`artifacts/T009/verify_coeff_amp_32_64.c`：四种最响模式 + 全列/全行交替 + 200 个 LCG 随机极值块，
**不读 T010 的文件**）。两侧数值**逐个吻合**：

| 几何 | fwd_tx_shift | log_scale | max\|coeff\| | max\|level\| | 上限 8191 的余量 |
|---|---|---|---|---|---|
| 4x4 | {1,10} | 0 | 8160 | 93 | 88.1x |
| 8x8 | {2,10} | 0 | 16320 | 185 | 44.3x |
| 16x16 | {2,11} | 0 | 32640 | 371 | 22.1x |
| **32x32** | **{3,12}** | **1** | **32640** | **742** | **11.0x** |
| **64x64** | **{3,14}** | **2** | **32640** | **1483** | **5.5x** |
| 4x8 / 8x4 | {1,11} | 0 | 11541 | 131 | 62.5x |
| 4x16 / 16x4 | {1,11} | 0 | 16320 | 185 | 44.3x |
| 8x16 | {1,12} | 0 | 23081 | 262 | 31.3x |
| 16x8 | {2,11} | 0 | 23081 | 262 | 31.3x |

三条要点（已由两侧独立数据支撑）：

1. **`max|coeff|` 从 16x16 起完全不再增长**：16x16 / 32x32 / 64x64 **恒为 32640**。
   T009 的独立复算里这条是**结构性断言**（`verify_coeff_amp_32_64.c` 要求 32/64 的 `max|coeff|` 与 16x16 严格相等，
   不等即 FAIL）。机理：正变换 pass-2 只跑 `min(w,32)` 行（`transform.c` 的 64x64 路径，`skip_line=32`），
   Q3 幅度被压住；`fwd_tx_shift` 的第二项 11->12->14 再进一步压低大尺寸。
2. **量化余量随尺寸单调变薄：22.1x -> 11.0x -> 5.5x**（16x16 -> 32x32 -> 64x64）。
   **禁止把 ≤16x16 的 22x 向上外推**（既有的定性警示由此获得实测支撑）。
3. **`SVT_AV2_QUANT_ERR_LEVEL_OVERFLOW` 在 `residual ∈ [-255, 255]` 下不可达**（最坏 `max|level| = 1483 << 8191`），
   是纯防御分支。另注：`log_scale = 1/2` 会把 level 再降一半/四分之一，故**大尺寸反而 level 更低**。

**T010 的一处自我更正 + T009 的解析闭环**（T009 引用时已采用更正后值）：

- T010 早先给 00 的**解析上界**把 64x64 算成 `2934 / 2.8x`，原因是解析式按单轴 N=64 叠加两次、
  **漏了 T009 pass-2 只跑 32 行**（64x64 出口是 32x32 网格）的上限。**2.8x 永久作废。**
  （T009 的 `{3,14}` shift 无误；错在 T010 的解析式。T010 已在 11:11 / 11:19 正式认领并更正。）
- **⚠ T009 自查更正（本条曾误引 T010 的 `32273`）**：本节早先写"改为 `min(N,32)` 后 64x64 解析上界
  = `32273 / 1467 / 5.6x`"——**这个 `32273` 是错的**。它等于 `16320 × 1.978 ≈ 32273`，即 T010 表中
  **8x8 那一格**的松上界（`T010.md:396` 与 `:399` 两行同值，属复制残留）。
  **判据**：`32273 < 32640`（实测）——一个"上界"低于它要界住的值，按定义就不是上界，故 `32273` 不可能是 64x64 的界。
  正确值（T009 自证，非引用）：**64x64 的 2-D DC 闭式 = `RS(RS(4096·255,3)·4096,14) = 32640`，与实测精确相等**
  （`artifacts/T009/verify_dc_closedform.c`，5/5 精确；同 `verify_coeff_amp_32_64.c` 实测 32640）。
  ⇒ **请用 `max|coeff| = 32640`（闭式=实测=精确值），不要用 `32273`。**
  `level` 侧同理：实测 `1483`（= `32640/22`），解析 `8191/1483 = 5.52x`；
  **`5.6x` 这个数原本由 `8191/1467`（= `8191/round(32273/22)`）得出，因分母含错值，请改用 `5.5x`（实测）**。
- **另一处刻度差（T009 新查，供双方记账）**：T010 解析表里 **4x4/8x8/16x16 的 `16137/32273/64547`
  恰好是实测 `8160/16320/32640` 的约 1.978 倍**（系数与 level 都是这个比值）。
  根因已由 T009 定位：真实 `max|coeff|` **恒落在 DC `(0,0)`**，而解析式取的是"最坏 AC 行和"型的累加，
  两者对同尺寸相差约 2 倍。即解析表是**松的上界**（DC 与最坏行的比值），**不是**实现差异。
  证据：`artifacts/T009/verify_maxcoeff_row.c`（证明 max 恒在 DC 且 DC 行和即最坏行和，ratio=1.000）
  + `artifacts/T009/verify_dc_closedform.c`（**纯解析**用 kernel 行和 + 冻结 shift 复现 2-D DC：
  `RS(RS(DCrowSum*255, s1) * DCrowSum, s2)`，与真实 kernel 输出 5/5 精确相等）。
  **附（T009 追加，供双方记账）**：T010 的 **64x64 行也填了 `32273`**（`T010.md:399`），与它 8x8 行（`:396`）同值
  ⇒ 是**复制残留**，不是 64x64 的界（见本节前一条）。T009 已在 `msg-t010-64x64-bound-copybug.txt` 要求其更正，
  并已按"闭式 = 实测 = 32640"修正本节。
- **"16x16 起不再增长"的解析机理**（由上一条闭式直接给出）：raw DC 在 16->32 与 32->64 各翻一倍，
  但 `s1` 在 32 多 1 bit、`s2` 在 64 多 2 bit，恰好抵消回 32640。

**§5b 追加：`max|level|` 列的第三方闭环（T009 独立复算，2026-10-07）**

上表 `max|level|` 一列由 T010 的量化器产生，T009 侧**无法直接测**，故 T009 改用**算术闭环**独立验证它：
用 T009 自己测得的 `max|coeff|` 除以**T009 从 AVM 源码独立复算的** level-1 反量化步长 `step`：

```
step = ROUND_POWER_OF_TWO(qlookup(100), 3) >> tx_scale
     = ROUND_POWER_OF_TWO(704, 3) >> tx_scale            (quant_common.c:130-136: 44<<4 = 704)
     = 88 >> tx_scale                                     -> 16x16: 88, 32x32: 44, 64x64: 22
```
